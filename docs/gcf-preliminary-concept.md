## Framework mapping and requirements

New route `gcf-preliminary-v1`, numeric version 1, displays **Preliminary project concept / Konsep awal proyek**. The eight sections are:

| Key | Supplied template section | Implementation |
| --- | --- | --- |
| summary | Project Summary | Explicit project title/location, project information and preparation-status table |
| rationale | Problem and Climate Rationale | Climate evidence, investment need and recalculated ECAM baseline, explicitly not climate projections |
| objectives | Project Objectives and Activities | Objective and selected-action activity table |
| benefits | Expected Results and Benefits | Indicator baseline/unknown targets and individual action benefit/caveat table |
| implementation | Implementation Approach | Organization, proposed partners, indicative duration and actual saved-plan task table |
| budget | Preliminary Project Budget and Financing | Cost categories with explicit unknowns, optional potential financing, no implied eligibility/commitment |
| risks | Preliminary Risks and Mitigation Measures | Risk/response table requiring project-specific assessment |
| next_steps | Information Required for the Next Stage | Explicit assumptions, outstanding studies/confirmations and preliminary conclusion |

Required *concept description* fields are title, country/location, organization, objective, climate problem/evidence, investment need, intended beneficiary group/service area and declared mitigation/adaptation purpose. Hazard/vulnerability evidence is conditionally required for adaptation/both. Duration and investment/currency are needed for further preparation but may remain explicitly unknown at this preliminary stage. Potential finance, partners and assumptions are optional. Training/capacity building is not automatically added as a necessary intervention. This classification is an explicit ChatWater workflow policy, not an official GCF application checklist; it awaits product/scientific confirmation.

`public/js/preliminary-concept.js` shares field definitions, conditional applicability, bounded input validation and sector resolution. Required unknowns become the existing editable placeholders; optional absence does not produce a required placeholder. Missing-information issues resolve independently by stable field code, even when multiple placeholders are in the same section. Source-field edits preserve text and make the prior concept outdated; regeneration remains explicit, with the old output retained in the existing previous-version slot. Human review never follows automatically from filling a field or writing a note.

## Action scope, generation and protection

Sector routing uses selected action locations: `ws*` → water, `ww*` → sanitation; mixed → both. Water-loss rules have water scope; a utility-wide solar action uses the actual assessment locations it addresses. The utility profile does not choose scope. Whole-assessment custom actions remain ambiguous unless explicitly classified; the draft explains uncertainty and does not guess a guide. Classification choices are bound to existing selected-action keys, not arbitrary assessment records.

The server retains assessment validity, selected-action ownership/figures, plan freshness, review and export checks. For the new route it reconstructs calculated action facts from current server options, preserving user notes/labels and custom user text. A client cannot replace a provisional caveat with misleading text. Existing erased-warning rejection also remains. Unknown or unsupported numerical results remain unavailable. Benefits are separate per action; combined effects, adaptation targets and financial benefits are not invented. Non-365-day assessment totals are not silently labelled annual or annualized.

The new prompt separates **recalculated project facts**, **explicit user inputs/assumptions**, **framework questions**, **retrieved guidance**, and **approved illustrations**. The last block states none are provisioned. Guidance retrieval is filtered to the exact selected-sector source IDs; those filters, queries, build IDs, passages, citation tags and qualifications are recorded. Existing `[S#]` citation syntax and screening semantics remain. AI-off text cites nothing; related reading is not represented as a citation. Empty/failed or quantitatively unsafe generated narrative falls back visibly to deterministic content; authoritative project tables are retained. This does not constitute comprehensive claim verification.

Existing document review is reused. Content/version/source associations include the preliminary metadata; changing it, editing sections or regenerating text requires review again. Interface-language switching does not. Invalid/mixed/stale project sharing stays blocked, including working-draft downloads. Server-selected scope excludes unrelated assessments and nested recovery data. Unknown/unsupported framework versions cannot be made to look current by relabelling them. A historical concept whose action classification cannot be validated against retained actions may be omitted from a scoped previous-version slot; the full recovery backup still preserves it without rebinding.
