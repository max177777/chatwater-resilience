## Semantics and coverage

`public/js/document-review.js` is the single UMD evaluator used by browser and server. `engine/document-review.js` supplies freshly calculated support and the existing `CW.freshness` context. Existing `FU.review`, placeholder/claim screening, `CW.mayBeIncomplete`, saved generation checks, source records and dependency checks are reused. Neither template origin, successful generation, legacy review ticks, a valid citation tag nor word overlap establishes human review.

- **Working draft:** at least one required content check, source/claim confirmation or section review is outstanding.
- **Reviewed:** every included document section passes the declared hard checks and has explicit human content/source/claim/warning confirmation bound to this version. It means editorial review, **not** scientific certification, fund eligibility or funder approval. Package/Word reviewed export requires both the retained plan and proposal to pass, because the plan and its tables are included in the supporting material. A proposal can show reviewed while upstream plan review remains outstanding; those plan issues remain listed and reviewed downloads stay disabled.
- **Outdated:** existing action/document dependencies changed. Review cannot rebind changed source data or bypass the existing regeneration/update workflow. Both export modes retain assessment support, source ownership, summed-benefit and freshness gates.

The plan's summary, each existing concept area and implementation schedule require review. Every proposal section requires review, including templates. Required information is the actual document's nonempty title/text, existing framework placeholders and task owner/name/duration fields. This does not invent a universal grant application completeness checklist or make optional utility-profile answers mandatory. A document without an existing concept does not acquire eight new mandatory concept areas; its actual summary/schedule are reviewed.

Hard unresolved checks prevent section confirmation: blank text, existing missing-information placeholders, incomplete AI text, unmatched current `[S#]` tags and missing/invalid task details. Source dependency changes prevent review/export. Failed generation/fallback origin, existing unsupported-figure/dropped-information flags, uncited funding/regulatory claim screening, source qualifications and provisional/unquantified action benefits require an explicit human confirmation **and a written treatment note**. A person can accept a manually completed fallback without concealing that generation failed. A source tag is only a locator; claim support must be read and assessed by a person. Provisional pump scientific warnings and custom-benefit limitations remain visible and exported; a review note never approves their methodology.

Issue buttons name their document and section, navigate/focus the content or assessment workflow, and work with Enter/keyboard. Review checkboxes and textareas are named by section; note errors use a focused alert. EN/ID status names, issue explanations, confirmations and download labels are in the shared evaluator. Source titles and saved document language remain as written. Broad WCAG/screen-reader certification and Silvia's terminology approval are not claimed.

## Binding, migration and races

`document.humanReview` version 1 stores one record per section: content/dependency association, explicit content/source-claim/warning confirmations, note and timestamp. Associations include section content and production/check metadata, saved output language, title, document dependency record, relevant evidence/source records and selected-action conditions/provisional warnings. Schedule review binds task details. Document-level associations enumerate the section associations and dependencies. Review metadata does not alter the existing plan fingerprint or scientific calculation revision.

Editing clears the edited section's valid review; prior note wording is retained as an editable `reviewNotes` draft requiring a new confirmation. Other unchanged sections retain review. Schedule edits reopen schedule review and existing proposal freshness; summary/concept edits also preserve the existing proposal-outdated behavior. A new/regenerated result clears previous review even for identical text. Language regeneration creates new text requiring review; changing interface language does not. Restoring a previous version re-evaluates its original associations/dependencies rather than marking it current. Valid bound reviews survive scoped backup round trips; legacy `reviewed:true` ticks preserve text but do not count as review. The old legacy-source association button is relabeled so it cannot be mistaken for human content review.

The review handler compares its rendered association with the current section before accepting confirmation, and is disabled during generation. `CW.regenerate` also compares the original object/content before committing; if another edit, restore, review or generation changed it, the response cannot overwrite the newer document. Failed/rejected responses preserve current text and review. A response cannot supply a reusable human-review record.

These are **local user attestations**, not authenticated signatures or reviewer identity verification. Export recomputes the state and required issues rather than trusting supplied `reviewed`/status flags. Wrong/stale associations and flags cannot override checks. A deliberately fabricated, fully matching attestation cannot be distinguished from a genuine user's attestation in this unauthenticated local-workspace model. Cryptographic audit/identity enforcement would need a separate product/security design; none is claimed here. Content associations reuse the existing noncryptographic change fingerprints, not tamper-proof evidence.
