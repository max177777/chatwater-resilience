## Shared contract and requirement coverage

`public/js/readiness.js` adapts the existing assessment validity, result-status graph, action support, `CW.freshness`, combined-benefit check and CW-10 document review. `public/js/readiness-ui.js` renders that contract; `engine/readiness.js` supplies authoritative recalculated inputs to the same adapter at read-only `POST /api/readiness`. This endpoint computes diagnostics and does not save anything or authorize exports. Existing downstream APIs remain the enforcement authority, including integrity/figure checks on supplied action records, metadata binding, ownership, validity and freshness.

Each issue has a deterministic ID, assessment/stage, blocker/warning/optional severity, localized message key, prevented operations, stable target and valid resolution choices. EN/ID explanations render through existing `UI` translations and CW-10 review wording. Field IDs use assessment ID, scope/substage ID and input code; custom actions use existing action keys, tasks use task IDs, proposal sections use framework keys and concept areas use framework IDs. Names and array positions are not persisted issue targets. Runtime positions are resolved only immediately before opening an existing form. Missing, ambiguous or deleted identities produce an explanation, never a replacement binding.

Coverage is operation-specific:

- **Assessment:** existing period/numeric/physical checks and enabled-process minimum inputs. Required numeric codes were extracted into `AV.requiredCodes` and reused by both validity and the adapter, without adding a second presence rule. A global minimum/date is labeled Required; enabled calculation/dependency inputs are labeled Required for this calculation; other fields remain Optional. Labels do not create new export prerequisites.
- **Availability/actions:** published result dependencies and all eight existing action support specifications. Unsupported optional calculations and benefits are warnings with named unavailable outputs; they do not become complete totals or quantified/ranked benefits. Action process coverage is shared with the existing engine via `RSData.ACTION_PREFIXES`; thresholds, scenarios and equations are unchanged. Selected custom-action location and saved-selection prerequisites reuse existing behavior.
- **Plans/proposals:** existing source/freshness checks, placeholders, generation screening, section review and source/claim confirmations. Requirements that prevent only reviewed export do not prevent otherwise valid working-draft export. Document, schedule and review controls describe this context explicitly. No universal funding/application checklist or mandatory standalone profile is introduced.
- **Always available through existing paths:** draft persistence/checkpoints and full workspace recovery backup. Storage errors remain handled by the existing recovery protections. Unknown, invalid, mixed or stale source information still cannot bypass the original downstream/export gates.

Explicit unknown is checked before blank display state, including a retained null value. ## Persistent UI and navigation

The existing four stage buttons show visible `!` blocker and `△` warning counts. A compact What needs attention panel follows the page heading, separates blockers from collapsed warning/optional lists, identifies the source assessment, and gives stage purpose, needed information, output and what may remain unknown. Each issue explains its own prevented operation; a blocked-operation attempt filters to relevant issues and focuses the summary. Counts are recalculated after edits without toasts or replacing the editing form. A debounced live region announces changed counts rather than rereading every issue on each keystroke.

Issue links open the owning assessment/stage, resolve process/section identities, expand relevant details, scroll/focus the control and associate an explanation beside it. Enabled review issues focus their confirmation; an outdated/disabled confirmation opens its editable note instead. Hidden fields lead to the process setting with an explanation; settings are never enabled automatically. Unavailable operation controls show an explanatory summary. Navigation preserves current text and never changes document dependencies or silently reassigns a plan/proposal. Selecting an action-source recalculation deliberately selects that source assessment, rather than borrowing the unrelated visible assessment.

Controls expose required/error context via `aria-required`, `aria-invalid`, labels and descriptions; process radios include the question name. Document requirements explicitly say that unfinished text may remain in a working draft. This is a bounded accessibility improvement, not a full WCAG or screen-reader certification.

### What the option clarification field actually does

The former “Add information or clarification for this option” textarea writes `state.actionNotes[actionKey]` on input and schedules local persistence. It does not invoke an API or trigger generation. “Save selection” copies that text to `selectedActions[].notes`. Action fingerprints include saved notes, so saving a changed selection can make existing downstream documents outdated. A custom action's draft note is also part of `CW.customDefs`, so its difference from the saved selection can already flag that selection for updating. These existing effects are preserved.

`engine/proposal.js` exposes the selected note as `user_notes` in facts consumed by drafting and explicit option explanation/alternative requests. Custom-action chat context can also include the note (bounded in length). These are potential prompt inputs when the corresponding feature is explicitly requested; typing does not request AI. With providers off, template/offline behavior remains in force. Notes survive full backups and source-scoped project metadata/selected-action JSON. They are not native ECAM inputs and are not guaranteed verbatim inclusion in generated prose or Word. Saving a note never confirms evidence, changes calculation inputs, or grants human review.

Both calculated and custom option cards now label this field **“Optional action context note”** / **“Catatan konteks aksi (opsional)”**, with the prompt **“Record local constraints, assumptions, or context for this option.”** / **“Catat kendala setempat, asumsi, atau konteks untuk opsi ini.”** The adjacent bilingual help explicitly explains local saving, Save selection, downstream drafting/exports, explicit AI requests, and the distinction from required document treatment notes. There is no new condition making an option context note mandatory.
